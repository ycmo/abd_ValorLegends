# Discord 遠端指令整合 QA

## 1. 核心需求與現況分析
* **目標**：透過 Discord 下達指令，讓常駐程式讀取訊息並觸發專案 (`adb_vl`) 內的特定腳本或功能。
* **現況盲點**：目前專案內的腳本（如 `setup_ads2.py`, `forge.py` 等）多為一次性執行或包含大量阻塞性 (Blocking) 的影像辨識與點擊操作。Discord 監聽需要非同步 (Asynchronous) 且常駐的環境，若直接混在現有流程中，極易造成互相卡死。

## 2. 架構選項評估 (請選擇)
為了保持架構穩定且不破壞現有程式，以下提供兩種選項供您評估：

### 選項 A：獨立的 Discord Bot 常駐服務 (推薦)
開發一個獨立的 `discord_bot.py` 負責常駐監聽特定 Discord 頻道。當收到指令時，透過系統呼叫 (`subprocess`) 去執行對應的現有腳本，並將執行結果或終端機輸出回傳至 Discord。
* **優點**：完全解耦，不會污染現有核心代碼。即使某個 ADB 腳本執行失敗或卡死，Discord Bot 仍能保持存活並接受中斷指令。
* **缺點**：需要同時管理兩個運行實體（Bot 本身與被呼叫的腳本）。

### 選項 B：基於 API / 佇列的微服務架構
建立一個輕量級的本地伺服器（例如 FastAPI + Redis / Queue），Discord Bot 和執行端（Worker）分離。Bot 收到訊息後把任務推入 Queue，專案主程式定期去 Queue 領取任務執行。
* **優點**：最為健壯，可支援複雜的任務排程與多工。
* **缺點**：實作成本較高，對目前專案來說可能過度設計 (Over-engineering)。

## 3. 待釐清的具體細節 (請回覆)
1. **預期指令清單**：初期希望 Discord Bot 能支援哪些指令？（例如：`!run_ads`, `!stop`, `!status` 等）
2. **執行回饋與截圖**：任務執行完畢或出錯時，是否需要 Bot 主動傳送現場截圖或 Log 到 Discord 頻道？
3. **權限控管**：是否需要限制只有您（特定的 Discord User ID 或 Role）才能觸發這些指令？
4. **Discord Token 準備**：您是否已經申請好 Discord Developer Portal 的 Bot Token？（我們將會使用 `.env` 檔來安全存放）
